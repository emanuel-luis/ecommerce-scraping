# Decisions

Low-impact decisions follow the recommended option of the refactor brief; high-impact ones
(history rewrite, licensing, paid services, anything irreversible or outward-facing) need the
owner's answer.

| # | Date | Decision | Choice | Why |
| --- | --- | --- | --- | --- |
| 1 | 2026-10-26 | Rewrite history to drop `products/` and `geckodriver.exe` | No rewrite | Only size is at stake (17 MB of 2022 CSV/JSON and a 3.2 MB driver); nothing secret was committed. A rewrite would break every clone for little gain. |
| 2 | 2026-10-26 | `README.md` / `readme.md` case collision | Keep `README.md`, drop `readme.md` (2022, pt-BR) from the index | Case-insensitive checkouts wrote one file over the other, so git reported `README.md` as modified. The old text stays in history. |
| 3 | 2026-10-26 | Tracked run output and binaries | Untrack `products/` and `ecommerce/bin/geckodriver.exe`; ignore them | They are crawl output and a vendored Windows binary, not source. |
| 4 | 2026-10-26 | Default branch | `main` (renamed on GitHub and locally before this refactor) | Program-wide decision. |
| 5 | 2026-10-26 | Which targets stay | Live: Hering, Levi's, TNG. Damyller: one saved page kept as a parser fixture only. Dropped: Afabula, Alphabeto, Daksul, Lupo, Marisa, Mormaii, Tricae | A polite probe on 2026-10-26 (robots.txt first, at most 4 requests per site, 3 s apart, identifying User-Agent) found that Hering, Levi's, TNG and Damyller allow their sitemaps and product pages and serve schema.org `Product` JSON-LD. The brief caps the live set at 2-3 stores; Damyller is the fourth. Daksul answers `robots.txt` with 403, Lupo moved to Shopify and answered 429 on the fourth request, Tricae now redirects to Dafiti, Mormaii disallows every URL with a query string and lists no sitemap, Marisa's product sitemap timed out, Afabula's product page has no structured data, and Alphabeto's sampled product redirected to the home page. Nothing is ever fetched against robots.txt or past an anti-bot response. |
| 6 | 2026-10-26 | Product discovery | The sitemaps listed in each store's `robots.txt` (`/sitemap.xml` -> `product-N.xml`) instead of category listings | The 2022 listing URLs use query parameters (`?PS=`, `?page=`) that several stores now disallow, and sitemaps are the crawl entry point the sites publish for bots. |
| 7 | 2026-10-26 | Extraction | schema.org `Product` JSON-LD instead of XPath on CSS classes | Server-rendered on every kept store, stable across theme changes, and typed (price, currency, availability, SKU, GTIN). The 2022 class-based selectors no longer match. |
| 8 | 2026-10-26 | JavaScript rendering | None: Splash, Selenium, the geckodriver and js2py are removed; scrapy-playwright is not added | The data the pipeline needs is in the server-rendered HTML of every kept store. |
| 9 | 2026-10-26 | Personal data in pages | Customer reviews (author names, review text) are never extracted or stored; saved fixtures have them removed | Hering's JSON-LD embeds reviews with customers' names. The pipeline only needs catalog data. |
| 10 | 2026-10-26 | Crawl vs. parse | Scrapy only fetches and lands raw pages; one offline `transform` step parses, validates, dedupes and writes Parquet | One parse path: reprocessing a run is the normal path, parsing is testable without Scrapy, and reruns are idempotent. Replaces in-crawl validation/dedupe item pipelines and a separate `reparse` command. |
| 11 | 2026-10-26 | What the raw layer keeps | Redacted pages: the canonical link and one JSON-LD block per schema.org `Product` node, without reviews, authors or any `Person` / `Review` node; no body, no other JSON-LD | Data minimisation by allow-list: the pipeline needs only the Product data, and some pages embed customer names. Committed fixtures come from the same redaction function. |
| 12 | 2026-10-26 | Storage | Parquet partitioned by `store` / `run_date` (written with DuckDB `COPY`), DuckDB views as the serving layer | File-based and analytics-friendly; one dependency writes and reads Parquet; views over files are idempotent. Same stack as books-scraping. |
| 13 | 2026-10-26 | Product key | Lowercased path of the final product URL (`/slug/p`) | Always present and unique per store; SKUs disagree between duplicate JSON-LD blocks on TNG and look like internal ids on Hering. |
| 14 | 2026-10-26 | Crawl size | 20 products per store by default, 10 in compose, 5 in `make demo`; first product sitemap only when limited | Keeps every run small and deterministic; a full Hering crawl would be 15,000+ pages. |
| 15 | 2026-10-26 | Blocked responses | A 403 or 429 (robots.txt included) stops that store's spider; 429 is not retried | Never push past a site that signals it does not want the traffic. |
| 16 | 2026-10-26 | Delivery | One PR on `refactor/ingestion-pipeline`; Step 0 fixes are separate commits inside it | The repo is small. |
| 17 | 2026-10-26 | pip-audit findings in Twisted 26.4.0 (pulled in by Scrapy) | Ignore the six advisories by ID in `security.yml` (GHSA-8pqf-f4m5-798g, GHSA-cwm5-jh59-mwxr, GHSA-2qrf-pqgx-qh9v, GHSA-3476-c5c2-fr73, GHSA-53xc-49m8-p798, GHSA-q7qq-6mhp-9rc4); remove the ignores when Twisted 26.10.0 is released | All six are in Twisted server code: the IMAP4 server, the conch telnet transport, the words XML element stream, the IRC server and the HTTP server's header parsing. Scrapy uses Twisted's HTTP client; the only server it could start here is the telnet console, which `TELNETCONSOLE_ENABLED = False` keeps off (a test asserts it). Five fixes exist only in the 26.10.0rc1 release candidate and one has no fix yet, so pinning a pre-release would not clear the audit either. Extended on 2026-10-27 with GHSA-jj36-9pvh-vj5r (CVE-2026-83813, low): DNS response spoofing in the `twisted.names` client, fixed only in 26.10.0rc1. It is not reachable here: no installed package besides Twisted imports `twisted.names`, and Scrapy resolves hosts with its default `CachingThreadedResolver` (a thread pool over the system resolver); `src/` sets no `DNS_RESOLVER`. All seven ignores go when Twisted 26.10.0 final is released. |
| 18 | 2026-10-26 | Scrapy's listening servers | `TELNETCONSOLE_ENABLED = False` and `REMOTE_CONTROL_ENABLED = False`; a settings test and the e2e assert both stay off | Scrapy 2.19 starts a remote-control HTTP server on a localhost port by default; it runs Python code posted with a bearer token stored in the user's profile. A batch crawl needs neither server, and the compose smoke showed the remote control failing to start in the container (no home directory). |
| 19 | 2026-10-27 | Diagrams as code | D2 sources in `docs/diagrams/`, rendered to SVG and committed next to them; the README shows the SVGs with a link to each source. The README's only Mermaid block (a four-node architecture flowchart) became `architecture` and `data-flow`. | Mermaid grows hard to read and to debug. Committed SVGs render on GitHub with no build, and the CI check proves they match their sources. Same standard as the owner's other portfolio repos. |
| 20 | 2026-10-27 | D2 version and render path | D2 v0.9.0 (latest stable on 2026-10-27), pinned in the Makefile with the sha256 of `d2-v0.9.0-linux-amd64.tar.gz` from the release's `SHA256SUMS`; `make d2-install` checks it with `sha256sum --check`. Layout engine ELK; never TALA. SVGs are rendered with the Linux binary only: WSL locally, `ubuntu-latest` in CI. | One version, one engine and one binary give the same bytes in both places, so `make diagrams-check` can compare with git. `*.svg -text` in `.gitattributes` keeps git from touching the bytes. |
| 21 | 2026-10-27 | Shared diagram style | `docs/diagrams/_style.d2` copied unchanged from the program's pilot: `vars.d2-config` (ELK, light theme 0, dark theme 200, pad 24, theme overrides), one shape per element kind, no explicit fills, a hand-made legend; the Makefile adds `--scale 1` and runs d2 under `env -i`. | Explicit fills stay fixed in dark mode and D2's built-in legend is a white box there; theme overrides on shapes follow GitHub's light and dark modes. `D2_*` and `SCALE` variables would override `d2-config`, hence the clean environment. |
| 22 | 2026-10-27 | Which diagrams | `architecture`, `data-flow`, `user-flows-cli-run` (`make demo`), `user-flows-compose` (`docker compose up`) and `data-model` (the five DuckDB views; keys are the grain each view guarantees). Each stays under about 1,300 px wide and 25 nodes. The `diagrams (D2 render check)` job is a required status check on `main`. | Proportional to a small repo: one diagram per question a reviewer asks (what runs where, how data moves and is checked, what a run does, what the tables look like). GitHub caps an SVG at about 980 px, so wider diagrams would shrink their text. |
